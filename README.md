# Food Order App — операционная консоль заказов

Fullstack-приложение для операционной команды доставки: список заказов
с фильтрами и нечётким поиском по адресу, карточка заказа с журналом изменений,
переходы по жизненному циклу, назначение курьеров с лимитом активных доставок
и корректная обработка конкурентного редактирования.

**579 тестов**: 165 доменных без БД, 266 интеграционных на реальном Postgres,
130 на интерфейсе, 18 e2e в браузере (включая автопроверку доступности).

---

## Быстрый старт

```bash
docker compose up -d --build
```

Всё. Одна команда поднимает Postgres, API и веб-сервер: миграции применяются
на старте, а пустая база наполняется демонстрационным набором
(20 ресторанов, 20 курьеров, 200 заказов).

Интерфейс — <http://localhost:8080>, API — <http://localhost:3000>,
документация API — <http://localhost:3000/docs>.

| Команда | Что делает |
|---------|------------|
| `docker compose up -d --build` | собрать и поднять стенд |
| `docker compose run --rm seed` | вернуть данные в исходное состояние |
| `docker compose logs -f api` | смотреть логи API |
| `docker compose down` | остановить |
| `docker compose down -v` | остановить и удалить данные |

Порты и параметры переопределяются через `.env` — см. [.env.example](.env.example):

```bash
echo "WEB_PORT=9090" > .env && docker compose up -d
```

### Разработка

```bash
pnpm install
pnpm db:up                        # Postgres в Docker
pnpm --filter @food/api migrate   # применить миграции
pnpm --filter @food/api seed      # 20 ресторанов, 20 курьеров, 200 заказов
pnpm --filter @food/api dev       # API на :3000
pnpm --filter @food/web dev       # интерфейс на :5173
```

Требуется Node.js ≥ 22, pnpm 11, Docker.

## Жизненный цикл заказа

```
new ──► accepted ──► preparing ──► ready ──► picked_up ──► delivered
 │         │            │            │
 └─────────┴────────────┴────────────┴──► cancelled
```

* Отмена доступна до `picked_up` включительно из `ready`; после передачи
  курьеру — запрещена.
* `delivered` и `cancelled` терминальны: недоступна и смена курьера.
* Переход в `ready` **требует назначенного курьера** — иначе заказ станет
  активным без исполнителя и правило лимита потеряет смысл.
  Это принятое допущение, оно продублировано ограничением в БД.

Граф задан данными в [`order-status.ts`](packages/contracts/src/order-status.ts)
и импортируется и сервером, и клиентом: интерфейс не показывает кнопку
недопустимого перехода, потому что читает тот же граф, что валидирует запрос.

## Ключевые решения

Каждое зафиксировано отдельным ADR в [docs/adr](docs/adr).

### Две разные гонки — два разных механизма ([ADR 0006](docs/adr/0006-concurrency-control.md))

**Потерянное обновление** (сценарий из ТЗ) — оптимистическая блокировка:
`orders.version` ведёт триггер БД, мутация идёт с `UPDATE ... WHERE version = ?`.
Ответ `409` содержит актуальный заказ и **перечень чужих изменений из журнала**:
«назначен курьер Alex», «статус «Новый» → «Принят»». Клиенту не нужен второй
запрос, чтобы объяснить оператору, что произошло.

**Лимит активных доставок** — здесь версия бесполезна: конфликтуют *разные*
заказы за общий счётчик курьера, и блокировать нечего — строки, которые станут
активными, ещё не существуют. Поэтому `pg_advisory_xact_lock` по конкретному
курьеру: заказы разных курьеров не сериализуются, лок снимается на коммите.

Проверено обратным экспериментом: с отключённым локом пять параллельных
переходов в `ready` проходят **все пять** вместо трёх.

### Домен — общий пакет, а не дубль на клиенте ([ADR 0001](docs/adr/0001-shared-contracts-package.md))

Граф переходов, бизнес-правила, коды ошибок и Zod-схемы живут в
`packages/contracts`. Правила — чистые функции, возвращающие код ошибки
и готовый русский текст, поэтому сообщение в API и в интерфейсе идентично
по построению.

### Инварианты продублированы в БД ([DATABASE.md](docs/DATABASE.md))

У таблицы `orders` больше одного писателя (API, seed, ручные операции),
поэтому `CHECK`-ограничения запрещают `ready` без курьера и отмену без причины,
а триггер делает журнал физически append-only: `UPDATE` и `DELETE` по нему падают.

### Повтор запроса не применяется дважды ([ADR 0012](docs/adr/0012-idempotency.md))

Оптимистическая блокировка не отличает «не применилось» от «применилось, ответ
потерялся». Мутацию можно пометить `Idempotency-Key`: результат сохраняется
в той же транзакции, что и изменение, поэтому повтор возвращает исходный ответ,
а не выполняет операцию заново. Клиент выводит ключ из самого действия, так что
защита работает и от двойного клика.

### Повтор запроса не применяется дважды ([ADR 0012](docs/adr/0012-idempotency.md))

Мутации принимают `Idempotency-Key`; результат сохраняется **в той же
транзакции**, что и само изменение, поэтому «применено, но не записано»
невозможно. Клиент выводит ключ из самого действия, а не генерирует случайно, —
поэтому двойной клик распознаётся как повтор, а новое действие получает новый ключ.

### Обновления в реальном времени ([ADR 0013](docs/adr/0013-realtime-updates.md))

Изменения публикует сама база: триггер на журнале шлёт `NOTIFY` — прикладной код
не может забыть отправить событие, а отклонённая операция не публикует ничего.
Доставка — Server-Sent Events. Список обновляется сам, открытая карточка
перечитывает заказ и показывает, кто и что изменил, — конфликтов стало меньше.
Механизм конфликтов при этом остаётся: поток может быть недоступен, и e2e
проверяют защиту именно в таком режиме.

### Время в статусе, а не «изменён N минут назад» ([ADR 0011](docs/adr/0011-status-sla.md))

`updated_at` двигает любое изменение, включая смену курьера, поэтому для поиска
залипших заказов он бесполезен. Отдельная колонка `status_changed_at` ведётся
триггером, нормативы на статус заданы данными в `@food/contracts` и
перекрываются переменной окружения. В списке есть фильтр «только просроченные»
и сортировка по времени в статусе — оператор сразу видит, чем заняться.

### Оформление подчинено задаче оператора ([ADR 0010](docs/adr/0010-visual-design.md))

Приглушённая палитра, один акцент, три семантических цвета: в списке из 200 строк
насыщенный цвет означает исключение. Статус передаётся цветом, точкой и текстом
одновременно — опора на один только цвет недоступна части пользователей.
Адаптивность сделана приоритетом колонок в той же разметке, без второго макета
и дублирования DOM.

### Поиск с опечатками ([ADR 0005](docs/adr/0005-fuzzy-address-search.md))

`pg_trgm` + GIN-индекс по генерируемой нормализованной колонке.
SQL-функция нормализации побайтово повторяет клиентскую — совпадение проверяется
тестом. Порог 0.5 выбран по измеренным оценкам сходства: полезные совпадения
дают ≥ 0.571, ложные (общие токены вроде «проспект») ≤ 0.448.

### Семантика HTTP ([ADR 0007](docs/adr/0007-http-semantics.md) · [API.md](docs/API.md))

Ошибки — RFC 9457 `problem+json` с машиночитаемым `code`.
**400** — схема, **422** — неисполнимый запрос, **409** — конфликт состояния,
**428** — не передан `If-Match`. Никаких `200 {"success": false}`.

### Seed прогоняет заказы через машину состояний ([ADR 0008](docs/adr/0008-deterministic-seed.md))

Заказ не «проставляется» в случайный статус, а проходит по графу переходов,
порождая согласованные журнал, версию и временные метки. Данные детерминированы
побайтово — включая UUID.

## Структура

```
packages/contracts   общий контракт: domain/ — правила предметной области,
                     api/ — схемы обмена; импортируется сервером и клиентом
apps/api             REST API: routes → services → repositories, миграции, seed
apps/web             React SPA: app/, api/, features/orders/, components/
e2e                  сценарии Playwright
docs                 спецификация, план, ADR, описание API и схемы БД
```

Подробная карта с правилом зависимостей и подсказкой «куда класть новое» —
[docs/STRUCTURE.md](docs/STRUCTURE.md).

Слои backend зависят строго внутрь: `routes` не знают про SQL, `services`
владеют транзакциями и блокировками, `domain` (в `contracts`) не знает
ни про БД, ни про HTTP и покрыт тестами без инфраструктуры.

## Проверка

```bash
pnpm lint && pnpm typecheck && pnpm test    # 561 тест, нужен Postgres
pnpm test:coverage                          # то же плюс пороги покрытия
pnpm test:e2e                               # 18 сценариев, включая проверку доступности
```

Покрытие удерживается порогами в конфигурации каждого пакета: прогон падает,
если оно просело относительно достигнутого. Доступность проверяется `axe`
на пяти состояниях интерфейса. Поведение блокировки под нагрузкой —
`pnpm --filter @food/api load:courier`.

E2E по умолчанию поднимают **изолированную** пару серверов на портах 3100/5174
поверх отдельной базы `food_orders_e2e`: сценарии создают и меняют заказы,
и делать это в базе демонстрационного стенда нельзя. База создаётся,
мигрируется и наполняется автоматически перед прогоном.

Против уже работающего стека (проверка реального развёртывания, без изоляции):

```bash
E2E_BASE_URL=http://localhost:8080 E2E_API_URL=http://localhost:8080 pnpm test:e2e
```

Готовые запросы для HTTP-клиента WebStorm — [apps/api/requests.http](apps/api/requests.http):
открыть, выбрать окружение `local`, выполнять сверху вниз. Пункты 6–8
воспроизводят конфликт версий.

| Команда | Что делает |
|---------|------------|
| `pnpm test` | тесты всех пакетов |
| `pnpm test:coverage` | то же с проверкой порогов покрытия |
| `pnpm test:e2e` | сценарии Playwright |
| `pnpm typecheck` | строгая проверка типов |
| `pnpm lint` / `pnpm format` | ESLint / Prettier |
| `pnpm db:up` / `pnpm db:down` | Postgres в Docker |
| `pnpm --filter @food/api migrate` | применить миграции |
| `pnpm --filter @food/api seed` | демонстрационные данные |

## Что сделал бы иначе при других масштабах

* **Пагинация.** Сейчас offset — для 200 заказов это правильный выбор:
  простой код и точный `total`. На миллионах строк `OFFSET 10000` заставляет
  Postgres читать и отбрасывать все пропущенные строки, поэтому нужен keyset
  по `(created_at, id)` — индекс под него уже есть. Точное общее количество
  пришлось бы заменить приблизительной оценкой.
* **Журнал изменений.** Append-only таблица растёт линейно с активностью.
  На больших объёмах — секционирование по месяцам и выгрузка старых секций.
* **Лимит курьера.** Advisory-лок держит транзакцию; при тысячах назначений
  в секунду на одного курьера он станет узким местом. Тогда — счётчик активных
  доставок отдельной строкой с `SELECT ... FOR UPDATE` либо материализованный
  счётчик с проверкой ограничением.
* **Аутентификация.** По условию не требуется; автор действия приходит
  заголовком `X-Actor`. В реальной системе на его месте — субъект из токена.
