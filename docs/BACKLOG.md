## M8. Время в статусе и просроченные заказы ✅

**Проблема.** Оператор видит «изменён 40 минут назад», но не видит, что заказ
**висит в `preparing` 40 минут при норме 15**. Поиск залипших заказов — основная
работа операционной команды, и сейчас инструмент её не поддерживает.

**Решение.** Колонка `orders.status_changed_at`, которую выставляет тот же
триггер, что ведёт версию. По ней считается время в текущем статусе и
сравнивается с нормативом на статус.

Решение и найденные при реализации грабли: [ADR 0011](./adr/0011-status-sla.md).

**Критерии приёмки**

- [x] `status_changed_at` заполняется триггером и не зависит от приложения
- [x] нормативы времени на статус вынесены в `@food/contracts` и в конфиг
- [x] API отдаёт `statusChangedAt`, `secondsInStatus` и признак `overdue`
- [x] фильтр `overdue=true` и сортировка по времени в статусе
- [x] в списке просроченные заказы визуально выделены
- [x] в карточке видно, сколько заказ находится в текущем статусе
- [x] тесты: триггер, расчёт признака, фильтр, отображение

## M9. Идемпотентность мутаций ✅

**Проблема.** `Idempotency-Key` объявлен в контракте, но не реализован.
При нестабильной сети повтор запроса создаёт второй переход и вторую запись
в журнале — журнал перестаёт отражать реальность.

**Решение.** Таблица `idempotency_keys` с уникальным ключом; запись **в той же
транзакции**, что и мутация. Повтор с тем же ключом и телом возвращает
исходный ответ, с тем же ключом и другим телом — `409`.

Решение и найденные при реализации грабли: [ADR 0012](./adr/0012-idempotency.md).

Решение и найденные грабли: [ADR 0012](./adr/0012-idempotency.md).

**Критерии приёмки**

- [x] повтор с тем же ключом не создаёт второй записи в журнале
- [x] повтор возвращает исходный ответ и исходный ETag
- [x] тот же ключ с другим телом отклоняется отдельным кодом ошибки
- [x] ключи с истёкшим сроком вычищаются
- [x] тест на параллельный повтор одного ключа

## M10. Обновления в реальном времени ✅

**Проблема.** Половина конфликтов версий существует только потому, что вкладка
не знает об изменении. Оператор узнаёт о чужой правке уже после нажатия кнопки.

**Решение.** `GET /orders/stream` на `text/event-stream`, источник событий —
`LISTEN/NOTIFY` в Postgres, публикация после коммита. Конфликты остаются
как последняя линия обороны, а не единственная.

Решение и найденные грабли: [ADR 0013](./adr/0013-realtime-updates.md).

**Критерии приёмки**

- [x] изменение заказа в одной вкладке обновляет список во второй без перезагрузки
- [x] открытая карточка показывает предупреждение до попытки изменения
- [x] переподключение при обрыве с экспоненциальной задержкой
- [x] поток корректно закрывается при остановке сервиса
- [x] тест: изменение через API доходит до подписчика

## M11. Готовность к боевой эксплуатации ⬜

- [ ] **Аутентификация и роли** — `X-Actor` подделывается, журнал теряет
      доказательную силу. Субъект должен приходить из токена.
- [ ] **Rate limiting** (`@fastify/rate-limit`) — один цикл в чужом скрипте
      выест пул соединений.
- [ ] **Метрики Prometheus** — латентность по эндпоинтам плюс счётчики
      доменных кодов. Всплеск `COURIER_CAPACITY_EXCEEDED` — это бизнес-сигнал
      о нехватке курьеров, а не техническая ошибка.
- [ ] **Трассировка OpenTelemetry** — где именно теряется время под локом.
- [ ] **Резервное копирование и проверка восстановления** — append-only журнал
      бесполезен, если его нечем восстановить.
- [ ] **Zero-downtime миграции** — политика «сначала расширяем, потом сужаем».

## M12. Масштаб данных ⬜

Всё перечисленное корректно на текущем объёме и сломается на большом.

- [ ] **Keyset-пагинация** вместо offset — `OFFSET 10000` читает и выбрасывает

- [ ] **Материализованный счётчик загрузки курьера** — сейчас коррелированный

- [ ] **Пересмотр advisory-лока** — при тысячах назначений в секунду
      на одного курьера он станет узким местом.

## M13. Продуктовые дыры ⬜

- [ ] **Позиции заказа** — сейчас заказ это сумма числом; оператор не может
      ответить на вопрос «что именно я заказал».
- [ ] **Расчётное время доставки и зоны** — без них нельзя ответить
      «где мой заказ».
- [ ] **Сегментация по городам.** Сейчас у заказа нет привязки к городу —
      только улица и дом, а «Пушкинская улица, 31» существует в десятках
      городов. Оператору нужно видеть заказы своего города.

      **Ключевое:** город должен быть отдельной колонкой, а не вычисляться
      из текста адреса при запросе — разбор свободного текста на лету
      медленный и ненадёжный. Проставляется один раз при создании заказа:
      либо приходит из системы-источника, либо через стандартизатор.

      Справочник адресов РФ (ГАР/ФИАС — официальный и бесплатный, но десятки
      гигабайт; КЛАДР — устаревший и компактный; OpenStreetMap — лицензия
      ODbL с share-alike; DaData — коммерческие подсказки на базе ФИАС)
      нужен **не для поиска**: поиск в консоли идёт по адресам уже
      существующих заказов, а не по каталогу. Реестр понадобится только
      для нормализации адреса при вводе и определения города.

      **Зависимость:** привязка «сотрудник → город» — это атрибут учётной
      записи. Без M11 её можно сделать лишь предпочтением интерфейса,
      которое любой переключит: это удобство, а не разграничение доступа.

      Критерии приёмки:
      - [ ] справочник `cities`, непустой `orders.city_id`, индекс `(city_id, created_at)`
      - [ ] фильтр по городу в API; поиск по адресу сужается выбранным городом
      - [ ] seed распределяет заказы по нескольким городам
      - [ ] город оператора запоминается и подставляется по умолчанию
      - [ ] точка расширения под стандартизатор адреса описана интерфейсом
- [ ] **Массовые операции** — назначить курьера на пять заказов разом.
- [ ] **Сохранённые фильтры** («мои проблемные»).
- [ ] **Отмена отмены** в течение 10 секунд.
- [ ] **Клавиатурная навигация** (`j`/`k`, `/` для поиска) — операционные
      инструменты этим живут.

## Решено по ходу

* **Сервис переживает перезапуск базы.** Пул сообщает об ошибке простаивающего
  соединения событием `error`; без слушателя это необработанное исключение,
  и остановка Postgres убивала процесс — восемь перезапусков контейнера подряд.
  Теперь ошибка пишется в лог, сервис остаётся жив, а `/health` честно отвечает
  `503 database: down`, пока база не вернётся.
* **Сервис `seed` переиспользует образ API.** Он собирался отдельным образом,
  и `docker compose build api` его не обновлял: данные загружались устаревшим
  кодом. Теперь оба сервиса указывают один тег.
* **Пустое тело при объявленном `Content-Type` равносильно отсутствию тела.**
  `DELETE /orders/:id/courier` отвечал `400 «Body cannot be empty»` клиентам,
  которые выставляют `Content-Type` всегда. Некорректный JSON по-прежнему
  отклоняется.

* **Изоляция e2e от демо-базы.** Сценарии создавали заказы вида
  «E2E Клиент 1787393113620» в той же базе, что обслуживает стенд, и осадок
  накапливался по 13 заказов за прогон. Теперь e2e поднимают собственную пару
  серверов на портах 3100/5174 поверх базы `food_orders_e2e`, которая
  создаётся и наполняется автоматически.

## Сознательно не делаем

| Предложение | Почему нет |
|---|---|
| Разнести на микросервисы | операционная сложность без выигрыша на этом объёме |
| Redis под кэш справочников | 20 ресторанов и 20 курьеров читаются из Postgres за миллисекунды |
| GraphQL | одна модель потребления данных, REST её покрывает |
| Event sourcing | журнал изменений уже даёт нужную часть пользы без цены полного перехода |
| Тёмная тема | инструмент дневной; токены вынесены, добавление — правка одного файла |
