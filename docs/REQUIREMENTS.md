# Карта соответствия: требование → код → подтверждение

Для каждого пункта технического задания указано **три вещи**: где решение
живёт в коде, чем оно закреплено (тест или ограничение БД) и как показать
его работу вживую.

Порядок пунктов повторяет порядок ТЗ.

---

## Сущности и жизненный цикл

| Требование | Где реализовано | Чем закреплено |
|---|---|---|
| Поля заказа | [`migrations/0001_init.sql`](../apps/api/migrations/0001_init.sql) — таблица `orders` | `CHECK`-ограничения в той же миграции |
| Ресторан, курьер | там же — `restaurants`, `couriers` | внешние ключи |
| Граф статусов | [`domain/order-status.ts`](../packages/contracts/src/domain/order-status.ts) — `ALLOWED_TRANSITIONS` | `order-status.test.ts` — таблица переходов продублирована независимо |
| Отмена только до `picked_up` | там же — `CANCELLABLE_STATUSES` | тесты, названные словами ТЗ: «граница из ТЗ» |

**Как показать.** Граф задан **данными, а не цепочкой условий**:

```ts
export const ALLOWED_TRANSITIONS = Object.freeze({
  new:       ['accepted', 'cancelled'],
  ready:     ['picked_up', 'cancelled'],
  picked_up: ['delivered'],          // отмена уже недоступна
  delivered: [], cancelled: [],
});
```

Тот же объект импортируют сервер и клиент. Отсюда следствие, которое стоит
показать отдельно: **интерфейс не рисует кнопку недопустимого перехода**,
потому что читает тот же граф, что валидирует запрос, — рассинхрон невозможен
по построению, а не по договорённости.

Проверка вживую: открыть заказ в `picked_up` — кнопки «Отменить заказ» нет;
попытка через API даёт `409 ORDER_NOT_CANCELLABLE`.

## 1. Список заказов

| Требование | Где | Чем закреплено |
|---|---|---|
| Все девять полей | [`OrdersTable.tsx`](../apps/web/src/features/orders/components/OrdersTable.tsx) — `COLUMNS`; ответ — `orderListItemSchema` | `OrdersPage.test.tsx` — «показывает все требуемые поля заказа» |
| Фильтры по статусу и ресторану | [`order-repository.ts`](../apps/api/src/repositories/order-repository.ts) — `buildFilters` | `list-orders.test.ts` — раздел «фильтрация» |
| Сортировка | там же — `buildOrderBy` | «сортирует по сумме численно, а не лексикографически» |
| Поиск с опечатками | там же — `searchCondition`; функция `normalize_address` в миграции | `seed.test.ts` — поиск по seed-данным |
| Пагинация | `paginate` в `services/mappers.ts`, [`Pagination.tsx`](../apps/web/src/features/orders/components/Pagination.tsx) | «разбивает выборку на страницы», «за последней страницей отдаёт пустой список» |

**Что показать в поиске.** Он не сводится к `LIKE '%…%'`:

* генерируемая колонка `delivery_address_normalized` + GIN-индекс `gin_trgm_ops`;
* SQL-функция нормализации **побайтово повторяет** клиентскую `normalizeSearchQuery`
  — совпадение проверяется тестом, иначе индекс и клиент разъехались бы молча;
* порог `0.5` подобран **измерением**, а не на глаз: таблица замеров
  в [ADR 0005](adr/0005-fuzzy-address-search.md).

Проверка вживую: `«Гордовикова»` находит `«ул. Городовикова»`, `«Молодежный»`
и `«Молодёжный»` дают одинаковый результат, `«Тверская улица»` — ноль.

## 2. Просмотр заказа

| Требование | Где |
|---|---|
| Карточка со всеми полями и журналом | [`pages/OrderPage.tsx`](../apps/web/src/features/orders/pages/OrderPage.tsx) |
| Изменить статус | `PATCH /orders/:id/status` → `OrderService.changeStatus` |
| Назначить или сменить курьера | `PUT/DELETE /orders/:id/courier` → `assignCourier` / `unassignCourier` |
| Отменить по бизнес-правилам | `POST /orders/:id/cancel` → `cancel` |

**Что показать.** Переходы оформлены **подчинёнными ресурсами**, а не
`PATCH` всего заказа: бизнес-переход не смешивается с редактированием полей.
Отмена намеренно сделана командой — она требует причины, и `PATCH /status`
её не принимает, это закреплено схемой (`transitionStatusSchema` без `cancelled`).

## 3. Конкурентное изменение — ключевой пункт

Здесь спрятаны **две разные гонки**, и одним механизмом они не закрываются.
Это главное, что стоит показать.

### Потерянное обновление

| Слой | Где |
|---|---|
| Счётчик версии ведёт БД | триггер `orders_bump_version` в миграции 0001 |
| Сверка до применения правил | `requireOrderAtVersion` в [`order-service.ts`](../apps/api/src/services/order-service.ts) |
| Условие при записи | `updateOrderWithVersion` — `UPDATE … WHERE version = $2` |
| Объяснение конфликта | `versionConflict` — собирает перечень изменений из журнала |
| Показ оператору | [`ConflictBanner.tsx`](../apps/web/src/features/orders/components/ConflictBanner.tsx) |

Барьера два намеренно: сверка **до** правил даёт понятный конфликт вместо
отказа бизнес-правила, посчитанного на устаревших данных; условие **при записи**
закрывает гонку между чтением и записью.

Ответ `409` содержит не «кто-то изменил заказ», а перечень: *«назначен курьер
Alex»*, *«статус «Новый» → «Принят»»* — плюс актуальный заказ целиком, чтобы
клиенту не понадобился второй запрос. Ради этого в журнал добавлена колонка
`order_version` (миграция 0002).

### Гонка на счётчике курьера

Версия здесь бесполезна: конфликтуют **разные** заказы за общий лимит,
их версии не пересекаются. Блокировать тоже нечего — строк, которые станут
активными, ещё не существует. Отсюда `pg_advisory_xact_lock` по конкретному
курьеру (`lockCourier`).

**Как доказать, что тест не проходит по совпадению.** Отключить лок и
прогнать `concurrency.test.ts`: пять параллельных переходов в `ready`
пройдут **все пять** вместо трёх. Это описано в [ADR 0006](adr/0006-concurrency-control.md).

Проверка вживую: e2e-сценарий «две вкладки: вторая получает конфликт вместо
перезаписи» в [`concurrency.spec.ts`](../e2e/concurrency.spec.ts).

## 4. Лимит активных доставок

| Что | Где |
|---|---|
| Правило | `checkCourierCapacity` в [`order-rules.ts`](../packages/contracts/src/domain/order-rules.ts) |
| Атомарность | `assertCourierHasCapacity` — лок **до** подсчёта |
| Проверка в двух местах | при назначении на активный заказ и при переходе в `ready` |
| Видно оператору заранее | `CourierDialog` показывает `2/3` и блокирует переполненных |

Тонкость, которую стоит назвать: слот занимают только `ready` и `picked_up`,
поэтому назначение курьера на заказ в `preparing` лимит не расходует.

Нагрузочная проверка: `pnpm --filter @food/api load:courier --orders 200` —
из 200 одновременных запросов применяется ровно 3.

## 5. Audit Log

| Требование | Где |
|---|---|
| Тип действия, старый и новый статус, время | таблица `order_audit_log`, миграция 0001 |
| Запись | `appendAudit` — **в той же транзакции**, что и изменение |
| Показ в карточке | [`AuditTimeline.tsx`](../apps/web/src/features/orders/components/AuditTimeline.tsx) |

**Что показать.** Журнал **физически** неизменяем: триггер `trg_audit_no_update`
отвергает `UPDATE` и `DELETE`. Это не соглашение в коде, а ограничение БД —
проверяется тестом в `schema.test.ts`.

Второе: запись идёт в одной транзакции с изменением, поэтому состояние
«изменено, но не записано» невозможно. Тест «не оставляет следов в журнале
при отклонённом переходе» это фиксирует.

## 6. Backend

| Требование | Где | Чем показать |
|---|---|---|
| REST | `routes/` — маршруты только разбирают запрос и вызывают сценарий | OpenAPI на `/docs` порождается из тех же Zod-схем |
| Семантика HTTP | [`problem.ts`](../apps/api/src/http/problem.ts), `error-handler.ts` | таблица кодов ниже |
| Валидация входа | `schemas.ts` — Zod | `400` с путями до полей в `details.issues` |
| Бизнес-валидация | `domain/order-rules.ts` — чистые функции | `409`/`422` с машинным `code` |

Разграничение статусов — то, что отличает продуманный API от «200 с полем
`success`»:

| Код | Смысл |
|---|---|
| `400` | запрос не прошёл схему |
| `422` | запрос корректен, но неисполним по данным |
| `409` | конфликт с текущим состоянием ресурса |
| `428` | не передан `If-Match` — молчаливая перезапись недопустима |

## 7. Seed

[`seed/plan.ts`](../apps/api/src/seed/plan.ts) — 20 ресторанов, 20 курьеров,
200 заказов с разными статусами, ресторанами, датами и курьерами.

**Что показать.** Заказ не «проставляется» в случайный статус, а **проходит
по графу переходов**: `progressPathTo()` строит путь по `ALLOWED_TRANSITIONS`,
каждый шаг порождает запись журнала с растущим временем и версией. Инварианты
соблюдаются по построению, а не проверяются постфактум — [ADR 0008](adr/0008-deterministic-seed.md).

Данные детерминированы побайтово, включая UUID: набор воспроизводится
командой `pnpm --filter @food/api seed`.

## 9. Аутентификация

Не реализована по условию. Автор действия приходит заголовком `X-Actor`
и попадает в журнал — [`actor-context.ts`](../apps/api/src/plugins/actor-context.ts).

Там же стоит показать неочевидное: значения заголовков по RFC 9110 —
байты latin-1, поэтому кириллическое имя приезжало искажённым. Обработчик
понимает и сырые UTF-8 байты, и процентное кодирование.

## Как провести показ

Порядок, при котором картина складывается за десять минут:

1. **`docker compose up -d --build`** — стенд поднимается одной командой,
   миграции применяются сами, пустая база наполняется.
2. **Список** — фильтры, поиск с опечаткой, сортировка по времени в статусе.
   Обратить внимание: состояние выборки целиком в адресной строке, ссылку
   можно переслать.
3. **Карточка** — журнал изменений, доступные действия, лимит `2/3` в диалоге курьера.
4. **Конфликт версий** — две вкладки либо пункты 6–8 в
   [`requests.http`](../apps/api/requests.http): `428` без `If-Match`,
   `200` с корректной версией, `409` с разбором изменений.
5. **Тесты** — `pnpm test` и `pnpm test:e2e`; показать обратный эксперимент
   с отключённым advisory-локом.
6. **[ADR](adr/)** — по одному решению на документ: контекст, альтернативы,
   следствия и то, что вскрылось при реализации.

## Что называть честно

Сильная сторона проекта — не объём, а обоснованность. В разговоре стоит
называть и **принятые допущения**, и **найденные при проверке дефекты**:

* переход в `ready` требует курьера — это трактовка ТЗ, а не буква;
* граница отмены взята из примера в ТЗ, и её сдвиг — правка одной строки;
* дефекты, найденные собственными тестами, описаны в разделах
  «Найдено при реализации» в [ADR](adr/) — они показывают, что проверка
  работает, а не что код был плох.
