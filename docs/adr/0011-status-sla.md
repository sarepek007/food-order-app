# ADR 0011. Время в статусе — отдельная колонка, а не производная от updated_at

**Статус:** принято · M8

## Контекст

Основная работа операционной команды — искать залипшие заказы, а не листать
список. «Изменён 40 минут назад» на этот вопрос не отвечает: `updated_at`
двигает **любое** изменение, включая смену курьера. Заказ, у которого только что
поменяли исполнителя, выглядел бы свежим, хотя в `preparing` он висит второй час.

Считать время в статусе на лету по журналу тоже нельзя: это подзапрос
на каждую строку списка, а фильтр «просроченные» превратился бы
в полный проход по таблице.

## Решение

Колонка `orders.status_changed_at`, которую ведёт тот же триггер, что и версию:

```sql
IF NEW.status IS DISTINCT FROM OLD.status THEN
    NEW.status_changed_at := now();
END IF;
```

Приложение её не выставляет — попытка подделать значение перетирается
триггером (закрыто тестом). При миграции значение восстановлено по журналу:
время последнего события, которым заказ пришёл в текущий статус.

### Нормативы

Заданы в `@food/contracts` как данные и перекрываются переменной окружения
`STATUS_SLA_SECONDS` — они зависят от города, кухни и времени суток.
Состояний четыре: `none` (терминальный статус), `ok`, `warning` (норматив
исчерпан на 80%) и `overdue`.

Расчёт — чистая функция в общем пакете, поэтому сервер и клиент одинаково
понимают, что считается просрочкой.

### Фильтр «просроченные»

Порог зависит от статуса, поэтому условие — дизъюнкция по статусам:

```sql
(status = 'new'       AND status_changed_at < now() - interval '5 minutes')
OR (status = 'preparing' AND status_changed_at < now() - interval '25 minutes')
...
```

Каждая ветка ложится на составной индекс `(status, status_changed_at)`,
и планировщик обходится `BitmapOr` вместо полного прохода.

## Следствия

* Оператор может отсортировать список по времени в статусе и увидеть сверху
  то, чем нужно заняться прямо сейчас.
* Просроченная строка выделена и **помечена текстом** — не только цветом.
* Плата: одна колонка и один индекс; нормативы приходится сопровождать,
  потому что «правильные» значения известны только эксплуатации.

## Найдено при реализации

Первая версия задавала колонке `DEFAULT now()`. Тест на вставку задним числом
показал, что при импорте и в seed значение расходилось бы с `created_at`:
заказ, созданный неделю назад, получал бы отметку «статус сменился сейчас».
Значение по умолчанию убрано, вместо него `BEFORE INSERT`-триггер подставляет
`COALESCE(status_changed_at, created_at, now())` — пропущенное значение
означает «заказ вошёл в свой первый статус в момент появления».
