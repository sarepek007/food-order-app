# ADR 0006. Две разные гонки — два разных механизма

**Статус:** принято · M3

## Контекст

В задаче спрятаны два независимых конкурентных сценария, и один механизм
не закрывает оба.

1. **Потерянное обновление.** A и B открыли заказ, B назначил Alex,
   A назначает Maria на устаревшем состоянии.
2. **Гонка на счётчике.** Два оператора одновременно выводят в `ready` разные
   заказы одного курьера. Заказы разные, конфликтует общий ресурс — лимит курьера.

## Решение

### Потерянное обновление — оптимистическая блокировка

`orders.version` ведёт триггер ([ADR 0004](0004-version-trigger.md)).
Мутация проходит два барьера:

* **до применения правил** — сверка версии, чтобы оператор получил понятный
  конфликт, а не отказ бизнес-правила, посчитанного на устаревших данных;
* **при записи** — `UPDATE ... WHERE id = $1 AND version = $2`; `rowCount = 0`
  означает, что кто-то успел раньше между чтением и записью.

В ответ уходит `409` с актуальным состоянием заказа и **объяснением, что именно
изменилось**: сервис читает журнал по `order_version > expectedVersion` и
превращает записи в текст «назначен курьер Alex», «статус «Новый» → «Принят»».
Клиенту не нужен второй запрос, чтобы показать разницу.

### Гонка на счётчике — advisory-лок по курьеру

```sql
SELECT pg_advisory_xact_lock(hashtextextended('courier:' || :id, 0));
SELECT count(*) FROM orders WHERE courier_id = :id AND status IN ('ready','picked_up');
```

Пессимистическая блокировка здесь обязательна: строк, которые можно было бы
взять `SELECT ... FOR UPDATE`, ещё не существует — заказ только собирается стать
активным. Лок берётся **по конкретному курьеру**, поэтому операции с разными
курьерами не сериализуются. Снимается автоматически на `COMMIT`/`ROLLBACK`.

Лимит проверяется в обоих местах, где заказ занимает слот: при назначении
курьера на уже активный заказ и при переходе в `ready`.

## Проверка

Механизм проверен не только позитивными тестами, но и обратным экспериментом:
с отключённым advisory-локом тест «пять параллельных переходов в ready»
пропускает **все 5** назначений вместо 3. С локом — ровно 3.
Тест на потерянное обновление воспроизводит сценарий A/B из ТЗ дословно.

## Альтернативы

* **`SERIALIZABLE`-изоляция** — закрыла бы обе гонки, но ценой ошибок
  сериализации на несвязанных операциях и обязательного ретрая в каждом вызове.
* **Уникальный индекс на «слот курьера»** — потребовал бы искусственной колонки
  с номером слота и превратил бизнес-правило в трудноизменяемую схему.
* **Блокировка строки курьера (`SELECT ... FOR UPDATE`)** — рабочий вариант,
  эквивалентный по эффекту; advisory-лок выбран, потому что не требует
  существования и изменения строки-«замка».
