# ADR 0007. Семантика HTTP-слоя

**Статус:** принято · M4

## Контекст

Операционной консоли нужны предсказуемые ответы: интерфейс различает
«поправьте форму», «так нельзя по правилам» и «кто-то вас опередил»,
и каждое состояние рисуется по-своему.

## Решения

### Ошибки — RFC 9457 `problem+json` с полем `code`

Клиент ветвится по машиночитаемому `code`, а не по тексту `detail`: тексты
меняются и локализуются. Коды и их HTTP-статусы объявлены в `@food/contracts`,
поэтому фронт знает их состав на этапе компиляции.

Разграничение статусов:

* **400** — запрос не прошёл схему. `details.issues[]` содержит путь до поля,
  форма раскладывает ошибки по инпутам.
* **422** — запрос синтаксически корректен, но неисполним (нет курьера, ресторан отключён).
* **409** — конфликт с текущим состоянием ресурса (переход, лимит, версия).
* **428** — не передано предусловие `If-Match`.

Никаких `200 { "success": false }`.

### Версия ресурса — `ETag` / `If-Match`

`GET /orders/{id}` отдаёт `ETag: "7"`. Изменение обязано вернуть эту версию
в `If-Match`; без неё — `428`. Поле `version` в теле оставлено как запасной путь
для клиентов, которым неудобно управлять заголовками.

`If-Match: *` означает «применить поверх текущего состояния» — это опора для
кнопки «применить моё изменение» в диалоге конфликта. Гонка при этом остаётся
закрытой: версия читается и тут же используется в `UPDATE ... WHERE version = ?`.

### Переходы — подчинённые ресурсы, а не PATCH всего заказа

`PATCH /orders/{id}/status`, `PUT /orders/{id}/courier`, `POST /orders/{id}/cancel`.
Бизнес-переход не смешивается с редактированием полей, каждый эндпоинт имеет
собственную схему и собственный набор бизнес-ошибок.

Отмена намеренно оформлена командой (`POST .../cancel`), а не установкой статуса:
она требует причины, и `PATCH /status` её не принимает — это закреплено схемой.

### Автор действия — заголовок `X-Actor`

Аутентификации в задаче нет, но журнал обязан хранить автора.

## Найдено при реализации

Проверка живого сервиса (не только `inject`) вскрыла дефект: значения HTTP-заголовков
по RFC 9110 — байты latin-1, и Node отдаёт их именно так. Кириллическое имя
оператора приезжало мусором (`Анна` → `ÐÐ½Ð½Ð°`) и в таком виде попадало в журнал.
Декодирование теперь понимает и сырые UTF-8 байты, и процентное кодирование;
строки, уже содержащие символы вне latin-1, не трогаются. Через `inject()`
дефект не воспроизводился — тестовый клиент передаёт заголовки как готовые строки.
