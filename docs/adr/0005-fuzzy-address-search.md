# ADR 0005. Нечёткий поиск по адресу на pg_trgm

**Статус:** принято · M3

## Контекст

Оператор ищет заказ по адресу, который часто продиктован по телефону:
«Лениский проспкт 12» вместо «Ленинский проспект, д. 12». `LIKE '%...%'`
такие запросы не находит вовсе.

## Решение

* Генерируемая колонка `delivery_address_normalized` + GIN-индекс `gin_trgm_ops`.
* Условие поиска — дизъюнкция трёх веток:
  * `q <% address` — word_similarity, ищет запрос как фрагмент внутри адреса;
  * `q % address` — similarity, сравнивает строки целиком (полный адрес с опечатками);
  * `address LIKE '%q%'` — короткие запросы вроде «21», которым не хватает триграмм.
* Ранг для `sort=relevance` — `GREATEST(word_similarity, similarity)`.
* Пороги задаются `SET LOCAL` в транзакции запроса, значение — из конфига.

## Выбор порога

Пороги подобраны по измеренным оценкам на тестовом наборе, а не на глаз:

| Запрос | Лучшее совпадение | word_similarity |
|--------|-------------------|-----------------|
| `Лениский проспкт 12` | Ленинский проспект, д. 12 | **0.571** |
| `Тверская` | Тверская улица, 7 | **1.000** |
| `Королева` (ё/е) | пр-т Королёва, д. 12 | **1.000** |
| `21` | наб. реки Фонтанки, 21 | **1.000** |
| `Владивосток Океанский проспект` | Ленинский проспект, д. 12 | 0.419 |
| `Мурманск Кольский проспект 8` | Ленинский проспект, д. 12 | 0.448 |

Полезные совпадения — не ниже 0.571, ложные — не выше 0.448. Порог **0.5**
разделяет их с запасом с обеих сторон. Ложные срабатывания возникали на общих
токенах («проспект», суффикс «-ский»), поэтому граница проходит именно там.

`SEARCH_SIMILARITY_THRESHOLD` вынесен в env: под другой набор данных
порог перенастраивается без правки кода.

## Следствия

* Поиск устойчив к опечаткам, регистру, пунктуации и различию ё/е —
  нормализация в SQL совпадает с клиентской (проверено тестом).
* Плата: GIN-индекс увеличивает стоимость вставки и занимает место.
  Для операционной консоли это выгодный размен.
* `SET LOCAL` требует транзакции даже на чтении — одна лишняя команда на запрос списка.
