## M1 — что сделано

`packages/contracts` — единственный источник правды о домене, импортируется и API, и веб-клиентом:

* `order-status.ts` — граф переходов данными (`ALLOWED_TRANSITIONS`), предикаты
  `isTerminal` / `isCancellable` / `occupiesCourierSlot` / `requiresCourier`;
* `order-rules.ts` — чистые проверки бизнес-правил, возвращающие `RuleResult`
  с кодом ошибки и готовым русским текстом (используется и сервером, и UI);
* `errors.ts` — коды ошибок, их HTTP-статусы, формат RFC 9457;
* `schemas.ts` — Zod-схемы запросов и ответов, из них же выводятся TS-типы и OpenAPI;
* `search.ts` — нормализация поискового запроса (общая для клиента и SQL);
* `audit.ts` — типы событий журнала.

Покрытие M1: 118 unit-тестов, БД не требуется.

## M2 — что сделано

* `docker-compose.yml` — Postgres 16 с healthcheck; init-скрипт заводит отдельную БД
  `food_orders_test`, чтобы тесты не трогали данные приложения.
* `apps/api/migrations/0001_init.sql` — типы, таблицы, ограничения, индексы, триггеры.
  Подробности: [DATABASE.md](./DATABASE.md).
* `src/db/migrate.ts` — раннер миграций: транзакция на миграцию, контрольные суммы,
  advisory-лок, идемпотентность.
* `src/db/schema.ts` + `client.ts` — Drizzle поверх существующей схемы.
* Конфигурация через env, валидируемая Zod при старте (`src/config.ts`).

Покрытие M2: 44 интеграционных теста на реальном Postgres.

### Дефекты, пойманные тестами

1. Триггер версии считал изменённой любую строку: в `BEFORE`-триггере
   STORED-генерируемая колонка ещё не вычислена, поэтому `NEW IS DISTINCT FROM OLD`
   всегда истинно. Холостой `UPDATE` инкрементировал версию и дал бы ложные конфликты.
2. `CREATE TABLE IF NOT EXISTS schema_migrations` при параллельном старте двух
   раннеров падал на `duplicate key ... pg_type`. Создание перенесено под advisory-лок.

## M3 — что сделано

Слои: `repositories` (единственное место, где known про SQL) → `services`
(транзакции, блокировки, журнал) → чистые правила из `@food/contracts`.

* `OrderService` — сценарии: создание, смена статуса, назначение/снятие курьера,
  отмена, список, карточка, журнал. Каждая мутация — одна транзакция:
  проверка версии → бизнес-правила → `UPDATE` с условием по версии → запись в журнал.
* Оптимистическая блокировка и advisory-лок по курьеру: [ADR 0006](./adr/0006-concurrency-control.md).
* Конфликт версий объясняется по журналу: «назначен курьер Alex»,
  «статус «Новый» → «Принят»» — плюс актуальное состояние заказа в теле ошибки.
* Нечёткий поиск с обоснованием порога: [ADR 0005](./adr/0005-fuzzy-address-search.md).
* Миграция 0002 добавила `order_audit_log.order_version` — она и делает
  точное объяснение конфликта возможным.

Покрытие M3: 110 интеграционных тестов (66 новых), включая 11 тестов конкурентности.

### Проверка качества тестов

Тесты на лимит курьера проверены обратным экспериментом: с отключённым
advisory-локом «пять параллельных переходов в ready» пропускает все 5 назначений
вместо 3. Тест ловит именно гонку, а не проходит по совпадению.

## M4 — что сделано

* Fastify 5 с Zod-провайдером: одни и те же схемы валидируют запрос,
  сериализуют ответ и порождают OpenAPI (`/docs`).
* Единый обработчик ошибок: доменные исключения, ошибки схемы и сбои
  сериализации приводятся к `application/problem+json` (RFC 9457).
* `ETag`/`If-Match` с `428` при отсутствии предусловия; `If-Match: *` —
  осознанное «применить поверх». Подробности: [ADR 0007](./adr/0007-http-semantics.md).
* Автор действия из `X-Actor`, готовность в `/health`, CORS с `exposedHeaders: ETag`.
* [requests.http](../apps/api/requests.http) — сценарии для HTTP-клиента WebStorm,
  включая воспроизведение конфликта версий двумя запросами.

Покрытие M4: 44 теста HTTP-слоя (всего в API 157, суммарно в проекте 275).

### Дефекты, пойманные на этом шаге

1. **Загрузка курьера всегда была нулевой.** Коррелированный подзапрос
   рендерился без квалификации таблиц: `WHERE "courier_id" = "id"` внутри
   подзапроса сравнивал две колонки `orders` между собой. Поймано тестом
   справочника курьеров, которого не было в M3.
2. **`DELETE /orders/:id/courier` отвечал 400 на запрос без тела** — Fastify
   передаёт `null`, а схема допускала только `undefined`.
3. **Кириллица в `X-Actor` попадала в журнал мусором.** Видно только на живом
   сервисе: `inject()` передаёт заголовки готовыми строками, а реальный HTTP —
   байтами latin-1.

## M5 — что сделано

Воспроизводимый набор данных: 20 ресторанов, 20 курьеров, 200 заказов,
992 записи журнала. Загружается одной транзакцией за ~60 мс.

Ключевое решение: заказ не «проставляется» в случайный статус, а проходит
по графу переходов из `@food/contracts`, порождая согласованные журнал,
версию и временные метки — [ADR 0008](./adr/0008-deterministic-seed.md).

```bash
pnpm --filter @food/api seed                 # 200 заказов, зерно по умолчанию
pnpm --filter @food/api seed -- --orders 50  # меньший набор
pnpm --filter @food/api seed -- --seed 42    # другой набор данных
```

Что получается на выходе:

| Свойство | Значение |
|----------|----------|
| Статусы | все 7, `delivered` ≈ 51%, `cancelled` ≈ 12% |
| Без курьера | 38 заказов (19%) — для empty-состояний и фильтра |
| Максимум активных на курьера | 3 — лимит не нарушен ни разу |
| Даты создания | последние 30 дней, свежие заказы чаще в ранних статусах |
| Адреса | одна улица в разных написаниях — для демонстрации поиска с опечатками |

Покрытие M5: 55 тестов (31 на генератор без БД, 24 на состояние базы).

## M6 — что сделано

React 19 + TypeScript + Vite, TanStack Query, React Router, Tailwind.
Решения и их обоснование: [ADR 0009](./adr/0009-frontend-state-and-conflicts.md).

**Список заказов** — все требуемые поля, фильтры по статусу (мультивыбор),
ресторану, курьеру и «без курьера», диапазоны суммы и дат, поиск по адресу
с опечатками (debounce 300 мс), сортировка по четырём полям, пагинация.
Состояние фильтров целиком в URL.

**Карточка заказа** — данные, журнал изменений таймлайном, действия:
переходы по статусам (только допустимые), назначение и смена курьера
с видимой загрузкой `2/3`, снятие курьера, отмена с обязательной причиной.

**Состояния интерфейса**: скелеты при загрузке, раздельные пустые состояния
(«заказов нет» и «ничего не найдено»), ошибки сети и сервера с повтором,
ошибки валидации по полям формы, бизнес-ошибки текстом сервера,
конфликт версий — отдельным баннером с разбором изменений.

Покрытие M6: 81 тест на MSW (перехват на уровне HTTP, а не подмена модулей).

### Проверка на живом стеке

Связка API + фронтенд поднята и проверена в браузере на seed-данных:
поиск «Королва 18» находит и «пр-т Королёва, д. 18», и «проспект Королева, 10»;
конфликт версий воспроизведён изменением заказа через API из другой сессии —
интерфейс показал «курьер Ольга Лебедева → Алексей Новиков» и обе версии,
кнопка «применить поверх» довела действие до конца.

## M7 — что сделано

* **Docker**: многостадийные сборки API и фронтенда, `docker compose up -d --build`
  поднимает Postgres, API и nginx с SPA. Миграции применяются приложением
  на старте, данные загружаются `docker compose run --rm seed`.
  nginx проксирует `/api` и пробрасывает `ETag` — без него клиент не смог бы
  прислать `If-Match`.
* **E2E**: 10 сценариев Playwright — список с фильтрами и поиском по опечатке,
  полный жизненный цикл с журналом, граница отмены после `picked_up`,
  и три сценария конкурентного доступа, включая две независимые вкладки.
* **CI**: GitHub Actions — lint, typecheck, тесты на сервисном Postgres, e2e.
* **README** с обоснованием решений и разделом «что сделал бы иначе при других
  масштабах».

Итог: 441 тест (118 доменных, 212 интеграционных, 81 на интерфейсе, 10 e2e).

### Замечание по e2e

Пять сценариев сначала падали на неоднозначных селекторах: названия статусов
встречаются и в бейдже, и в журнале изменений. Исправлено не подгонкой
ожиданий, а добавлением устойчивых точек привязки в разметку
(`order-status`, `order-courier`).

## Доводка оформления

После M6 проведена точечная доработка визуальной части — без смены стека
и без изменения поведения: [ADR 0010](./adr/0010-visual-design.md).

* Палитра и типографика вынесены в токены `@theme`, цвет используется
  как сигнал об исключении, а не как украшение.
* Статус передаётся цветом, точкой и текстом одновременно.
* Плотность таблицы, липкая шапка, `tabular-nums` для сумм и номеров.
* Адаптивность через приоритет колонок: на узком экране второстепенные
  колонки сворачиваются в подстроку под именем клиента. Одна разметка,
  без дублирования DOM.
* Иконки — инлайн-SVG без внешней зависимости, все декоративные.
* Журнал изменений — лента с соединительной вертикалью и иконками событий.
* favicon, `color-scheme`, описание страницы.

Все 441 тест остались зелёными. Один дефект поймал тест: подстрока под
именем клиента дублировала сумму, уже показанную в своей колонке.
